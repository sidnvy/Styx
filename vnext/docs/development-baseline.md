# 共享开发基线

Styx 的公共集成分支是 `develop`。功能分支从 `develop` 建立，评审和验证后回到 `develop`；`main` 只接收经过评审、具有交付范围和验证记录的发布基线。平台目录或一台电脑上的开发副本不是另一套公共 Core。


## 当前收敛：原生更新与实际组件一致

本轮实现位于 `feature/core-platform-upgrade-20261022`，尚待最终原生安装链验收后回到 `develop`。App 文件的安装、替换和卸载交给平台发行机制；Core 保留同一份配置、身份、Host 迁移记录及恢复规则。安装新版 App 不等于已更新 Host，启动时必须按包内组件核对已安装版本。

- macOS 接入可选 Sparkle 标准更新界面及 AppKit 正常退出；仅有有效更新源的构建才显示更新入口。候选包没有发布更新源，不能称已完成正式在线更新。
- Windows 私有文件权限改用包内固定哈希的原生 Windows ACL 读取器，保留实时检查和拒绝不明确权限。相同状态的全量读取从约 30.1 秒降至 9.8 秒；这仍不是即时响应。更新失败后，失效的读取会重新发起一次，失败提示不会被刷新覆盖。
- 原生 App 只按 Core 明确授权尝试一次随包 Host 更新。准备检查之前就记录事务，失败或取消后重开不会默默重试。用户明确选择恢复时复用同一套事务。
- Linux 新安装使用稳定 `install/node` 路径及 systemd `Type=exec`，仍等待真实连接就绪。旧包生成的、精确匹配且已停止并禁用的服务定义可加入现有 Host 迁移事务；更新和回滚均对账并重新加载 systemd，不修改系统目录权限、不自动启动服务。

### 2026-10-23：先固定生命周期，再展开下一批开发

当前产品冻结为 `c392c8b` / `0.3.0-rc.20261022.9`。`16b9dfc` 只将已有 Windows 原生安装器回归接入日常质量检查和平台 CI，不改变产品。完整本地工程检查通过；原生交付仍逐平台记录，不能据此宣称整机重启、账号侧或正式分发通过。

后续不是重新实现一套框架，而是按以下责任与退出条件收拢现有实现。界面变化必须先有对应用户动作、结果和失败返回路径；后台变化必须先明确所有者与实际验收。

| 范围 | 权威与责任 | 不重复实现 |
| --- | --- | --- |
| App 安装、文件替换和卸载 | Mac 的平台更新集成、Windows Inno、Linux 发行包；签名与文件占用遵循平台机制 | Core 不另造 App 安装器或强制退出器 |
| 用户配置、身份、配对及 Host 迁移 | 同一 Core API 与现有事务；状态、计划、执行及恢复共用 | App/CLI 不分别保存角色或恢复规则 |
| 进程生命周期 | 实际创建者拥有其子进程；登录服务由系统服务管理器负责 | 不按模糊名称杀进程，不让多个监督器争相重启同一组件 |
| 运行和连接状态 | 实际进程/服务观察、认证连接、真实工具结果分别提供证据 | enabled、PID 存在、本地通道在线均不等于用户任务成功 |
| 权限与账号 | OS 授权及目标聊天账号各自为准 | 不在本地配置伪造系统权限或聊天验收 |

| 用户/系统事件 | 固定产品行为 | 决定性验证 |
| --- | --- | --- |
| 关闭设置窗口 | App 继续运行，保留已有任务 | 窗口关闭后同一真实任务可继续 |
| 明确退出 App | Core 检查所属工作；正在执行或状态不明时明确反馈；准许后正常退出所属组件 | 活跃命令不中断；空闲退出后所属进程消失，独立 CLI 服务不受影响 |
| 安装并打开新版 | 平台安装器替换 App；Core 核对随包 Host，只对已授权且可信的新目标尝试一次迁移 | 真正旧包→新包，无额外 Update 点击；实际进程使用新 Host，真实 Exec 成功 |
| 更新失败或中断 | 保留原配置、身份、旧 release 与事务；重开进入明确恢复，不默默重复执行 | 保留失败现场；用产品恢复入口恢复后再执行真实命令 |
| 登录、注销和重启 | 按既有启动设置及真实会话恢复；没有桌面会话不报告 Computer Use 就绪 | 真实系统事件后验进程、连接、权限与任务结果；子进程重启不能冒充整机重启 |
| 断网及恢复 | 用既有身份重新认证；不重建配对，不重放结果不确定的命令或 GUI 操作 | 同一身份恢复连接；旧引用/不确定结果按既有会话规则处理 |
| 撤销设备 | 旧凭据失效；关闭邀请窗口不撤销已配对设备 | 旧凭据实际被拒绝，已批准设备关闭邀请后仍可重连 |

下一批的固定顺序与范围：

1. **结束已运行的 rc9 验收并回收基线。** 每平台只跑安装/升级→真实任务→正常退出重开→必要回滚这条链。沿用未变化的 Browser/Cua 证据；失败先定位责任边界，不同时重建其他平台或扩充测试矩阵。
2. **补已确认的旧 Linux 双角色升级缺口。** 仅允许精确匹配当前公开生成器、已停止禁用的 Gateway user unit作为现有 Host 事务的只读绑定；验证签名运行时、路径、定义和原生状态。独立 Gateway 不迁移；使用 Host 稳定 Node 的已知 legacy 定义只复验绑定。未知历史 runner、修改过的 unit、额外 drop-in继续要求明确迁移审查，不猜信任。用真实旧 Host 服务与独立 Gateway 服务完成升级、实际 Exec及回滚；不新增配置文件、事务框架或自动卸载重装。
3. **补 Mac 登录启动与更新的已确认冲突。** 正常退出会卸载当前登录任务并保留未来登录偏好；原离线守卫却因 plist 仍存在拒绝更新。只从现有 `app-lifecycle` 注册和签名链派生内部只读绑定，将精确定义、存在状态和偏好接入已有 candidate/plan/journal，执行与回滚重复核对。只允许固定当前用户路径的已登记且已卸载定义；loaded、foreign、修改过的定义继续拒绝，不加外部豁免开关、不删除或重新安装登录任务。验收限于“开启登录启动→正常自动升级→真实 Exec→偏好原样”和“任务仍 loaded→拒绝且零写入”；无需新权限、签名身份或服务框架。
4. **补产品验收而非扩功能。** 按现有角色与服务实现核对整机重启/登录、断网恢复、新用户聊天端的缺口。涉及共享测试机的系统事件先确认影响范围；账号登录与系统权限由用户完成。平台差异先在一个最小真实样例中验证，再接主流程。Mac 桌面恢复要求图形登录；测试前明确登录操作者、实际 FileVault 状态和重启后的可达入口，不能把 SSH 恢复当作桌面就绪。
5. **发行准备单独决策。** 公共代码签名、公证及真实更新源按各平台发行方式处理；开发签名、手动安装和本地升级成功不能替代正式分发。CAS/通用长期任务沿用已有独立设计与记录，不能混入本轮生命周期补丁或误称已经由普通安装包提供。

每个子任务开始前写清：现有机制、所改文件、用户可见结果、一条成功路径、一条有决定性影响的失败路径、验证后的结束条件。若新发现要求改变所有者、信任、安装布局或恢复契约，先回到这张责任表审查；不在平台适配器里临时增加第二套状态机。相同输入且未变化的通过检查不重复运行；修复有实际新影响时才扩大检查范围。

平台参考：[Sparkle](https://sparkle-project.org/documentation/)、[Inno 默认占用检查范围](https://jrsoftware.org/ishelp/topic_setup_closeapplicationsfilter.htm)、[Windows Restart Manager](https://learn.microsoft.com/en-us/windows/win32/rstmgr/about-restart-manager)、[systemd service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)。这些机制解决平台职责，不能替代 Styx 的任务、身份和配对契约。

1. 先确认 `develop` 的来源 revision、干净状态和当前集成记录，再建立 `feature/...` 分支。明确本次行为、平台范围与验收边界。
2. 公共 Core、权威配置、API、Exec / Computer Use / Browser 三项能力的选择与状态、会话和资源归属在同一分支体系内修改。平台 UI 和原生适配调用这些契约，不维护第二份角色配置，也不各自定义配对、会话或恢复规则。

4. 合并前更新到受审查的 `develop`，检查差异并运行受影响的契约、集成和平台检查。涉及共享配置、签名闭包或生命周期时同时核对其他平台；文案修改不因此触发无关的全平台重建。
5. 从明确 revision 和完整输入清单构建候选。记录实际产物及未覆盖门槛，再决定是否把该候选提升为 `main` 发布基线。合并、发布文件和部署到已有设备是独立动作。

## 每个平台都要记录的来源

每次交付记录源码 revision；若混合来源，分别列出公共 Core、平台 UI/适配的 revision 和经过审查的文件差异。还需保留实际 source closure（输入文件清单与哈希）、依赖锁、工具链/原生组件版本与哈希、签名或包内一致性检查、产物哈希和检查 receipt。`HEAD` 相同不证明本机未提交文件、漏拷贝依赖或既有安装与该产物相同。

临时隔离源码回灌先核对来源和差异，再应用到明确的测试副本。未确认的远端执行结果不算完成；不能覆盖另一线程未提交工作，或顺带替换已装 App、后台任务、服务、权限和私有状态。
