## 最初调试轮次的可运行修改

- 同一个 Core 审批 API 接受精确设备身份，能力从 Gateway 的当前已验签申请派生。旧调用者重复提供能力时必须一致，不能趁审批更改能力。
- 两端公开核对摘要包含本次 request ID、设备公钥指纹、连接 origin 和 TLS 叶证书摘要；它是公开比较指纹，不是连接密钥或新认证协议。既有 TLS、签名、加密领取和独立批准机制保留。
- 私有 HTTP 状态仅白名单投影核对码，不暴露完整执行证据或凭据。当前申请的普通 UI 不再接受旧的 16 位设备指纹代替本次核对码；高级完整指纹路径保留。
- Windows 接入邀请/待确认设备页面，并把本机准备、等待确认、读取审批失败、本机检查受阻、结果不确定分别呈现。结果不确定的安装和请求不会自动重复。
- 当时对未接通的独立入口停止邀请创建。后续附加入口已接通，但保留同一 Gateway、原聊天配置和精确入口授权；本机探测仍不能代替远端可达。

## 端到端验收还缺什么

1. 已连好聊天的普通主台，在原 App 中添加另一台电脑，同时保留原身份、证书、隧道、本机 Host 和账号连接。
2. 两台真实 App 完成邀请、同次核对、领取和连接，再从原 ChatGPT 账号指定新电脑运行真实 Exec/所选能力。
3. 错误核对、抢用、过期、撤销和身份变化的普通用户恢复流程；关闭配对窗口后批准 Host 的实际重连已有上述物理证据。
4. 对实际交付版本分别验收 Windows 交互 Cua、重启/登录/注销/锁屏/网络恢复及各平台升级/回滚。已有执行器崩溃恢复和 Linux 独立升级记录，不能因此宣称整机生命周期或任意新构建均通过。
5. macOS 稳定签名责任链及新装/升级权限、正式组件和真实聊天账号验收，继续由 Mac 本机线程负责。
