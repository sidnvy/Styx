# 从现有 Styx 演进到 v6 产品

2026-10-20。状态：基于已确认产品逻辑的实施基线；不是功能或发布完成声明。

## 1 采用的演进方式

保留现有 Gateway、Host、Exec、Cua、Core、设备身份和配对体系；将 v6 的原生产品界面逐页接到同一 Core，再补生命周期、多设备入口、迁移和验收缺口。Browser 在独立工作树开发，冻结可审查的提交后集成。

原型中的页面位置可以由 App 保存；设备角色、安装、进程、配对、凭据和恢复仍由现有权威配置及 Core 管理。不能将原型的本地布尔状态带进产品作为第二套运行状态。

每阶段交付一条可运行、可验证的用户路径。第一条是单机首装到真实聊天；下一条是添加另一台电脑；随后完成跨平台、升级与完整发布验收。期间的开发候选按实际范围标记，不能称完整正式产品。

## 3 已固定的产品约束

- 欢迎页只有开始设置、加入已有 Styx。语言默认跟随系统，通过 Styx 设置进入系统单 App 语言设置。
- CLI、Browser Automation、Computer Use 是三个独立执行能力。Agent 选择工具；本地负责授权、设备定位和确定性的协议转发。
- 普通用户的 Browser 首阶段采用受管理的专用浏览器；网站登录按需由用户完成。不把 CDP、profile 或技术角色作为首装选择。
- 关闭窗口继续运行；退出停止 App 管理的组件及其当前恢复，不立即被拉起；登录启动是独立设置。CLI 独立管理、且不属于 App 的进程不能被误停。
- 单机默认本地 Gateway＋Host；加入已有仅建立 Host，不新建 Gateway、聊天 Tunnel 或插件。
- 日常页面为概览、电脑、聊天连接。活动入口暂隐藏；已有 CAS Run/Wake 和执行／恢复记录保留。
- 使用用户提供的正式黑白品牌图标，源资产见 `../assets/brand/`，不再用字母占位符。
- 系统权限、官方账号登录／MFA／工作区审批、网站登录由用户完成；App 自动完成获准的本机准备和检查。

## 4 现有实现与真正需要改的地方

| v6 功能 | 可直接复用 | 必须补的连接或行为 |
| --- | --- | --- |
| 新建／恢复本机 | `core.mjs`、`local-setup.mjs`、部署及 journal | 四个用户阶段映射现有内部步骤；现有部署继续原进度，不能重复创建身份 |
| 原生窗口与设置 | `Styx.swift` 的 AppKit 生命周期、菜单、Cua owner、私有 setup 启动 | 增加原生视图与类型化 Core 客户端；替换旧七步网页主界面 |
| 三类能力 | 当前 Exec/Cua；独立 Browser provider | 统一请求、授权、就绪和实际验收投影；旧 Host 不因新增字段自动获准 Browser |
| 平台两项信息 | 隧道 configure/start/health、私有 Key 文件 | 接入固定输入输出；只读状态不泄密；本地 ready 不等于账号可用 |
| 插件创建／关联 | `plugin-flow.mjs` 的资料、记录与导出；`account-acceptance.mjs` | 解除官方直接创建路径对 ZIP／上传确认／必填插件 URL 的强依赖；保留可选导出与旧记录兼容 |
| 真实聊天测试 | Exec 证据、Cua 动作与读回、独立来源确认 | 合入 Browser 实际证据；原生视图替换后修正旧 DOM 读回桥，保持真实性要求 |
| 生命周期 | foreground/background、平台服务与登录恢复 | 消除首装必选前台／后台；统一跨进程观测、退出归属、崩溃对账与登录恢复 |
| 添加电脑 | 一次性邀请、TLS 预检、独立审批、加密领取、撤销基础 | 受控入口准备／迁移、精确网络范围、两端 UI、续证、撤销 Core/UI 操作与真实跨机验证 |
| 升级／回滚 | Gateway 更新事务、Host 低层更新、原生监督器离线迁移 | Host 托管更新执行尚明确 blocked；补候选隔离启动、实际健康与身份检查，以及统一恢复 |
| 会话与长任务 | owner 隔离、已移除数量拒绝、CAS 持久账本 | 补资源回收和未知结果对账；不恢复数量上限，不复制 CAS 账本，不将活动页作为首版前置 |

两个已在源码中确认的冲突：

1. `plugin-flow.mjs` 的新建记录要求当前 ZIP 导出、上传确认及特定插件 URL；v6 接受官方页面直接创建／安装。需要真实的记录模型兼容改动，不能只把页面上的上传按钮隐藏。
2. `journey.mjs` 仍把 background preference 当作必答步骤，`core.mjs` 保存 foreground/login 选择；现有登录恢复又可能把 Quit 后的 App 拉起。v6 要求把窗口关闭、App 退出和下次登录启动分别实现。

## 5 macOS 界面的实现落点

在现有 AppKit App 中逐步嵌入 SwiftUI 产品视图，保留 App delegate、进程监督与 Cua owner。通过 `NSHostingView` 实施局部替换，避免把整套 App、权限宿主和运行组件同时换掉。此接口是 Apple 支持的 AppKit／SwiftUI 集成方式。[Apple NSHostingView](https://developer.apple.com/documentation/swiftui/nshostingview)

现有 Node Core 继续负责配置、安装与运行，不重写成 Swift，也不复制一套安装器。原生客户端复用当前私有控制端点和受保护启动交接；普通状态与敏感交接分开。不能为了原生客户端绕过既有 owner、Origin／CSRF、参数白名单或凭据保护。

生产代码保留稳定 Bundle ID、发布身份与组件 ownership。UI 换成原生控件不等于 TCC 责任链已正确，Exec 子进程权限归属仍需单独实测。

特别处理 Cua 验收：当前证据含网页 DOM 读回。原生视图必须提供真实控件的受控读回，仍绑定当前 App PID、窗口、快照、challenge 与真实动作；不能把模型回显或用户勾选替换成成功证据。

旧 WKWebView 在开发阶段保留为内部诊断／回滚入口。原生路径通过后，从普通产品导航移除旧引导，不长期给用户两套设置入口。

## 8 首批实际开发的边界

第一批以“新原生界面能完成已有真实单机路径”为目标，包含：

1. 增加原生产品视图和同源、受保护的 Core 客户端；保持现有运行组件和 App 身份入口。
2. 页面只绑定 Core/OS 的真实投影；配置不存在显示欢迎，旧配置恢复真实阶段；普通导航不显示活动。
3. 修正插件官方直接创建／复用的记录语义，同时兼容旧导出记录和选择方式；URL 是可选定位信息，真实调用与来源确认仍必需。
4. 把前台／后台技术选择移出首装，先完成关闭窗口保持可用的行为；退出与登录恢复的互锁作为这一批的联调重点。
5. 接入正式图标和中英文资源；完成原生编译、控件／键盘走查以及 Core API 回归。

这一批不扩充活动中心、通用自主任务 UI、现有浏览器多种接管方式或发现／中继服务。已有 CAS 和三类工具选择规则保留。

## 9 迁移和验收必须保留的边界

- UI 阶段与内部执行 journal 分离，不为四个用户步骤重建内部安装记录。旧 foreground/login 意愿需要有明示的映射和执行记录，不能凭读状态就安装新服务。
- 增加 Browser 不变更旧设备的身份，也不把 requested 升格为 authorized。覆盖旧 Host／新 Gateway、新 Host／兼容 Gateway 的能力协商，拒绝不支持的组合并给出明确原因。
- 配置、运行时和服务定义在同一受控事务中生成；更新前核对当前实际状态和归属。保护仍在运行的任务；未知命令或 GUI 结果先对账。
- 保留 Gateway／Host 身份、批准关系、凭据引用、专用 Browser profile 和插件关联。备份及回滚记录不进入公开日志、聊天或包。
- 权限由 OS 决定。保持签名标识仍需实测；ad-hoc→正式签名、签名身份改变、升级和回滚不能预先保证免授权。禁止改 TCC 或关闭系统保护。
- Mac 主台＋Windows Host、headless 主台＋桌面 Host 都要验收。Windows Host 基础不等于完整 Windows 桌面 App；普通 GUI 加入体验需要单独补齐和报告。
- 六种角色组合保留；Gateway-only 包和 headless Gateway 不安装 Exec/Cua/Browser，headless Host 不声称 Computer Use 就绪。
- 隔离测试先行。Pilot Mac 可做已授权的开发验收；NAB／piermini 的真实服务变更要协调，不借发布测试修改故障排查现场。
