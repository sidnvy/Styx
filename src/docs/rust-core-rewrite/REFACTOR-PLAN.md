# Styx 架构：一个 Gateway，多台 Host

2026-11-14，所有者已确认以下产品行为。本文是本轮重构的目标；当前实现仍有下文列出的差异。

## 一次调用与两种角色

模型入口只有一条：**ChatGPT → OpenAI Private MCP Tunnel → Gateway → 选定的 Host → 执行器**。结果沿原路返回。一套部署有一个 Gateway，只有它持有 Tunnel 配置和凭据。Host 主动连接配对时指定的 Gateway。网络由用户提供，Tailnet、站点间路由或局域网均可；Styx 使用可直达的地址，并报告连接结果。

**Gateway 是设备目录和路由中心。** 它持有邀请、设备信任与撤销记录，观察哪些 Host 在线，并向 ChatGPT 提供管理和执行入口。可使用这个 MCP 入口的人都拥有整套部署的管理权限，包括生成邀请、移除设备和请求变更 Host 设置。部署共用一个管理范围；对话标识用于选择资源和延续上下文。设备身份验证、Tunnel 身份验证和本机系统授权继续有效。

**Host 是本机设置、执行与结果的负责人。** Exec、Browser、Computer Use 的开关由 Host 保存并执行。在本机设置和在 ChatGPT 中要求修改，最终调用同一个 Host 操作。Host 成功应用后报告实际能力；需要系统授权时报告等待授权。Gateway 按 Host 报告的能力路由。关闭某项能力立即拒绝后续调用，并停止该能力已启动的任务；其他能力、设备连接及配对继续保留。三个能力全关仍能接收设置请求。开关不替换 Host 或整个执行器；执行器依照 Host 生命周期退出。安装器负责安装与更新的完整验签。Rust Core 共享身份、协议及操作规则；GUI、CLI 和 headless 服务按需要组合角色。

## 无运行时配额（2026-11-15）

所有平台统一取消 Styx 自设的设备、对话、任务、并发请求、会话和历史记录配额。
不通过增加配额、平台特例、额外队列或自动重试解决 `capacity_busy`。普通读取不能因其他
对话正在使用同一 Host 而被拒绝。各执行器的实际资源操作顺序、系统权限、协议消息格式
与关闭中的生命周期检查继续有效；未知结果仍不能重放。

验证必须覆盖同一 Host 上两个独立调用者的重叠调用，以及其中一个结束后另一个继续读取、
执行和使用已有资源。超过原来的固定上限仍应可用；历史仅按原有任务归属和明确清理结束，
不得为接纳新任务而驱逐其他任务。Windows、Linux 和 macOS 使用同一共享实现。

## 安装、配对与更换中心

| 安装方式 | 首次设置完成时的用户体验 |
| --- | --- |
| macOS、Windows、Linux 桌面 · Host-only | 输入 Gateway 地址与一次性短码，本机确认加入，选择本机能力。也可以一次粘贴地址和短码。整个向导只有设备侧设置。 |
| 同三种桌面 · Gateway + Host | 在向导中配置 Tunnel，这一步必做。本机自动成为第一台配对设备，直接选择本机能力。之后其他设备用邀请加入。 |
| Linux headless · Gateway-only | 现有服务管理器启动 Gateway；CLI 可以先生成邀请、接入设备，再配置 Tunnel。Gateway 独立运行，无需图形会话、浏览器或本机执行器。 |

桌面 Host 的能力初始值为 Exec 默认勾选且可取消，Browser、Computer Use 默认关闭。生成邀请即批准一台设备加入。可手输的短码一次有效，首次配对仍需认证正确的 Gateway；协议选型、码长与过期时间属于实现决定，优先采用成熟配对机制。设备重连沿用身份和配对。已配置设备在本次软件重构中保留身份；用户主动换 Gateway 时，旧中心先列出受影响设备，新中心配置 Tunnel，各台 Host 分别用新邀请重新加入。

## 设备选择和操作归属

一个对话可使用多台 Host。每次执行落到一个明确设备。用户点名或上下文清楚时沿用该设备；只有一台已配对 Host 时默认选它；多台且目标不明时询问。选定目标离线就报告离线，其他设备即使在线也不会接手命令。

| 能力 | 用户可依赖的行为 |
| --- | --- |
| Exec | 任务归执行它的 Host。关闭对话或临时断线，已开始的任务继续；在同一次 Host 运行期间，另一段对话可以查询结果、进度或停止原任务。 |
| Browser | 每段对话默认有独立浏览器会话，原对话结束后仍保留。明确要求接手时保留原标签页与页面状态，随后由新对话操作；同一会话只接受当前操作者。明确关闭、关闭 Browser 能力、收到设备撤销或退出 Host 才结束会话；Host 重启不恢复。 |
| Computer Use | 多段对话可以使用同一 Host。并发交由该平台的 Cua 处理，Host 如实报告忙碌、目标失效与操作结果。沿用上游目标观察和输入语义，无需新增对话级整桌面锁。当前调用不扫描其他对话的执行器，也不合并其他对话的权限作为准入条件。 |

Browser 与 Computer Use 优先沿用**固定版本**的 Playwright、Cua 工具与参数。Host 报告本机实际可用的工具，Gateway 根据目标公开或路由受支持的调用。上游升级时核对有实际差异的适配和行为。

## 断线、退出和撤销

| 事件 | 行为 |
| --- | --- |
| 派发前已知 Host 离线 | 立即报告“未发送”；再次上线后由用户重新发起。 |
| 提交中连接丢失 | 查询原操作能否被确认；无法确认时保留“结果未知”，不自动重发。已开始的任务按对应能力的生命周期继续。 |
| 主动退出桌面 Styx | 只有「退出 Styx」一个动作。本机停止自己承担的全部角色，收回自己管理的任务，保留已生成文件；下次启动不自动续跑。Host-only 只令本机离线；组合模式同时关闭 Gateway 和 Tunnel，其他 Host 保留配对，等原中心恢复后重连。 |
| 移除设备 | Gateway 立即撤销配对、停止派发并拒绝旧身份重连。在线 Host 收到撤销通知后停止所管理的任务；离线时报告“配对已撤销，远端任务是否停止无法确认”。重新加入需要新邀请。 |

## Exec 边界的实现落点

Host 运行时的 `exec_tasks` 保存本次运行的任务目录、输入与输出读取状态、停止操作记录及最后一段完成结果。Core 继续负责操作身份、派发证据和执行器清理；任务使用 Host 本地的所有者身份，不使用对话的访问身份。连接重建和 Gateway 进程代际变化只更新调用方访问，不重建任务。Host 退出仍由现有 Core 生命周期收回执行器和任务。调用方访问记录与单连接约束也属于 Host 运行时，协议适配器重建不会创建另一套任务或访问身份。清理句柄与运行时容器保持单向引用，避免退出后自我持有。

普通 EOF、网络超时和 Gateway 停止只结束连接。Gateway 仅在确认对应设备的持久撤销记录后，使用已认证 WebSocket 的应用关闭原因通知 Host；Host 将明确撤销与暂时断线区分，走同一条本机停止清理路径。撤销接口明确报告远端任务停止尚未确认，不把关闭帧发送成功当成进程退出证据。重连遇到永久准入拒绝按首次连接的同一规则结束 Host，暂时故障继续等待原中心。

Gateway 的公开适配只选择设备并转发 `host_exec_tasks_v1` 调用，不保存 Exec 任务表、输出游标或任务归属。旧 Host 未声明此能力时不启用新的 Exec 路由，避免静默使用会在聊天关闭时杀进程的旧行为。低层 prepare/dispatch 接口保留给现有私有协议消费者，公开 Exec 入口只走 Host 任务控制。

`list_execution_tasks` 查询所选 Host；`write_stdin` 和 `stop_execution_task` 使用同一设备和任务 ID。完成结果在本次 Host 运行期间可重复读取，内容是最后一段输出，并非完整日志；运行中输出由调用者共用一个读取位置。`pending` 表示尚未观察到完成，不能据此断言进程仍在运行。结果未知时检查原任务，不能自动重新执行命令、输入或停止操作。Host 重启不会恢复任务表。

## Browser 边界的实现落点

Host runtime 的 `browser_sessions` 持有会话目录、当前操作者和 Core 资源句柄。
Browser 资源使用 Host 本地租约，对话只授权本次访问；聊天清理和 Gateway 连接替换
不结束浏览器。Gateway 不保存会话、操作阶段或页面引用，也不承担转交判断。

`list_browser_sessions` 查询当前 Host 的保留会话；`take_over_browser_session`
是明确的接手动作。常规 Browser 工具可带 `browser_session_id`，省略时使用当前对话
默认会话；指定 ID 本身不能接手。原操作者继续操作会被拒绝，不静默创建替代浏览器。
转交与操作使用同一会话互斥，进行中返回 Busy；转交不换执行器、不复制 profile，
只变更操作者并失效该会话的旧引用。新操作者重新观察页面。结果未知不自动重放。
Browser 输入准备任务也归 Host runtime，重建协议对象不能丢失其生命周期。
Linux/Windows 移除旧的单 Browser worker 门禁，与 macOS 一样按执行器实际分配
有界通信缓冲；不同会话可以共存，同一个会话仍串行操作。

新 Gateway 仅在 Host 协商 `host_browser_sessions_v1` 后提供 Browser 路由；旧 Host
不能静默回退到由 Gateway 持有会话的语义。私有 v3 底层 Browser 操作保留给现有协议
消费者与回归测试，公共 MCP 统一走 Host 会话端口。升级安装与跨平台实际运行另行验收。

2026-11-15 实施约束：两端普通导航现按“电脑 / ChatGPT / 通用”组织，只有一个“更新 Styx”
用户操作。Rust 在原更新记录中完成准备、提交与恢复连接；界面不维护第二套更新事实。
主窗口、应用菜单和托盘应复用同一设置窗口，而不只是复用同一个 View。实机已发现并
移除 macOS 在引导结束后仍另外创建 Settings 窗口的路径；回归检查窗口身份及关闭重开。
更新按钮只包装一次异步操作，版本来自安装组件记录；一次完成反馈不能保存会过期的
连接状态。当前安装、重启与独立读取结果见交付计划最新检查点，未通过的实机项不能用
编译、截图夹具或用户入口背后的直接 Core 调用代替。

先做角色组合和配对：用 headless Gateway 接入桌面 Host，再用桌面组合模式自动加入本机并接入第二台 Host。两种拓扑都应只配置一次 Tunnel。GUI 强制完成 Tunnel 和 CLI 延后配置分别从各自正常入口验证。

随后打通 ChatGPT 的设备管理与按设备执行：在一个对话中分别选中两台设备，以实际效果确认目标；从 ChatGPT 和本机变更同一能力，并核对 Host 实际状态。最后按发生顺序验证断线、跨对话继续、主动退出和撤销，确认已完成的动作不会重放。每迁移一个职责，就移除已经被接管的调用方判断；现有格式或接口仍有消费者时先处理兼容。

同机角色是否共用进程、是否走回环、crate 如何划分均为实现选择。先复用现有同机 Host 和远程 Host 的路由；只有具体用户行为需要时才增加分支。参考分支的类型和模块拆分按此取舍。


本地 Host 停止结果分别携带 `stop_reason` 与原 executor/process/I/O/job 清理事实。
运行失败或配对撤销不再丢弃已经取得的清理证据；普通 CLI 退出按本地资源是否结束返回，
远端 transport 未确认仍原样报告 Unknown。App 沿用同一结果办理本地退出，
安装/维护交接的严格条件保持独立。
