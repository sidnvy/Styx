# 如果从头设计 Styx

2026-11-14，架构提案。代码参照 `develop@99e0cd4`，工程整理参照 `refactor/engineering-review@bec7df1`。

## 用户买到的能力

用户把一台电脑配给 Gateway，随后就能从模型客户端选择这台电脑，执行命令、操作浏览器或使用桌面。电脑断线时能看出它离线，重新连接后仍认得它。桌面用户能直观地知道退出 Styx 对本机有什么影响。Linux、macOS、Windows 都保留 Gateway 和 Host 角色，二者可以同机运行。

我会围绕这些承诺设计。每多一个常驻进程，先说出关掉谁之后它还应该工作；每多一项持久状态，先说出重开之后用户还应该得到什么。它们的答案决定进程边界和存储边界。crate 数量、现有 IPC 方法、历史验收步骤都可以随实现改变。

## 我会交付什么

| 部分 | 谁负责什么 |
| --- | --- |
| Gateway | 接受 MCP 请求，核对授权，找到已经配对的 Host，转发并返回结果。设备离线能如实报告。一台桌面退出不影响其他电脑。 |
| Host | 主动连接 Gateway，管理这台机器的执行任务。命令交给 Codex，浏览器交给 Playwright，桌面交给原生权限上下文中的 Cua。执行器由实际创建它的一方收尾。 |
| Rust Core | 用库表达共用的身份、授权与操作结果规则，由 Gateway 和 Host 调用。Core 这项代码职责本身无需独立守护进程。需要隔离或原生权限归属的执行器可以有各自的进程。 |
| 桌面 App 和 CLI | 提供设置、配对、状态和运行入口。App 使用本平台的事件循环、权限和菜单，CLI 使用同一套 Rust 管理能力。安装器及更新器持有版本切换和完整包校验。 |

默认桌面模式下，App 启动一个归它持有的本地运行实例，把本次选择的 Host 或 Gateway 角色组合进去。关闭设置窗口保留菜单栏或托盘运行，选择“退出 Styx”结束本实例。确实要独立常驻的角色，由用户显式配置，交给操作系统现有服务管理器；这时桌面 App 只是客户端，退出界面后服务继续运行。已有部署沿用其原所有者。macOS、Windows 的新服务安装属于已推迟的交付范围。

存储保留配对身份、授权、角色与用户配置，以及协议确实需要跨崩溃保留的少量操作事实。窗口是否关闭、某轮连接是否断开、某个子进程是否还活着，由当前运行实例观察。重新打开时读配置、建立新连接；结果未知的外部写入保留未知，绝不因重开而重发。日常启动打开已经安装的版本，完整验签在安装或更新时完成。

## 用 Quit 检查这个设计是否说得通

目前 Mac 已使用 AppKit 的退出回调，Windows 也已使用 WinForms 的应用上下文。上层回调仍要解读 Rust 的退出许可、启动结果、维护状态和原先启动的子进程是否已清理。仓库记录过一次 Windows 实例已完成本地清理、却因 Gateway 不可达而报告 Quit 失败的事件。11 月 4 日已纠正这个具体问题。这说明一旦把普通退出定义为分布式操作，补对框架回调仍会反复出错。[Mac 入口](../../host/macos/Styx.swift) · [Windows 入口](../../host/windows/Styx.cs) · [历史修正](ADR-035-LIVE-HOST-DRAIN.md)

从头实现时，桌面模式的正常路径只有“框架收到退出 → 停止自己启动的本地实例 → 框架结束”。框架允许异步收尾时，由一个完成回调接回事件循环。Host 停止接新任务，按既定任务策略收尾，等待自己启动的 worker。远端自行观察连接断开。服务客户端模式只需关闭自己的连接和界面。

如果用户的命令仍在运行，“退出时允许取消吗”是产品行为，应该明确并在 Host 处理一次。目标设计不预设强杀、后台续跑或自动重试。现有任务处置语义在迁移时保留。App 异常消失时，单靠 GUI 退出回调无法回收子进程；这一处由创建进程的适配器用原进程句柄、连接关闭或系统进程管理能力处理。该能力用真实 worker 核实。更新过程需要独占一套安装文件时，协调放在更新入口。

## 怎样从现有仓库走过去

1. **先保留一条能工作的主线。** 用现有 Gateway、Host 和执行器，经正常产品入口在已配对设备上执行一条有可见结果的命令。画清这次运行中谁启动了谁、谁写配置、谁向用户返回结果。重用现有协议、身份和签名，同一个工作区里推进。
2. **把一个桌面入口做薄，随改随删。** 先选已有明确失败记录的 Windows App 管理模式。复用原生应用上下文、现有 Rust 实例和进程句柄，让普通 Quit 只依赖本地所有权。用“Gateway 不可达仍可正常退出，重开后用原配对恢复”验证；同步移除被替代的 GUI 判断和退出许可依赖。随后在 Mac 接入同一职责划分，保留它自己的 AppKit 和权限宿主。若发现既有代码已满足目标，直接保留它。
3. **用同一标准处理其余职责。** 配对拒绝归入配对代码，角色切换归入角色管理，更新归入安装更新流程。哪个现有入口确实迫使调用方推断别人的状态，就迁移哪个。有效测试继续覆盖用户承诺；依赖旧内部步骤的断言随实现调整。工程整理分支中的类型改进、文件拆分和依赖提取按需采用。已有 `develop` 上的 macOS 修复继续保留。

## 仓库应该怎样指导 agent

我会让根指导只回答三个问题：Styx 对用户承诺什么，哪些决定由哪一层作出，这次修改怎样从用户入口验证。设备与签名的真实限制继续保留；命令放在 WORKSPACE，发包细节放在发布技能，过去的故障留在对应测试和历史记录。

给维护者的默认指令可以很短：**先用框架或上游的常规做法实现用户动作。若需要新增进程、持久状态或跨组件协议，说清哪项用户承诺依赖它。改完后删掉已被接管的旧路径。** 用下一次真实改动观察新维护者能否仅凭这些入口找到负责人、完成修改并停在恰当的验证层级。这份提案供架构决策使用，日常任务无需通读。

技术参照见 [AppKit 退出回调](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationshouldterminate%28_%3A%29)、[WinForms 应用上下文退出](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.applicationcontext.exitthread?view=windowsdesktop-10.0) 和 [Windows 进程组管理](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。
