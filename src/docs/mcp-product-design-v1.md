# Styx MCP 接入设计 v1

日期：2026-10-20。状态：评审稿；基于源码 `d219c45` 核对。本文描述下一版目标，不表示 Browser、按需加载或账号接入已经实现。

## 1. 设计结论

**一个 Styx App／CLI 管理入口，一个用户侧插件连接，一个 Gateway MCP 入口，内部三个执行 provider。Agent 选择工具，本地执行已授权的调用。**

| 层 | 职责 |
| --- | --- |
| ChatGPT／Codex Agent | 理解目标、拆分步骤、选择 Exec／Browser／Cua，判断是否换一种工具 |
| 插件与 MCP 目录 | 提供简洁说明、稳定工具 schema、设备能力与实际状态 |
| Gateway | 身份、配对与能力授权、设备定位、调用归属及确定性的工具名分发 |
| Host | 本机连接、Exec 生命周期、可选 Browser 和 Cua 的连接与生命周期 |
| App／CLI／Core | 共用权威配置与管理 API，提供权限入口、安装、启动、停止、状态和恢复 |

不增加本地推理 Agent、任务语义分类器、Terminal 黑名单或 GUI 任务审批。按工具名分发是协议转发，不替 Agent 选择执行方法。Gateway-only 无需安装浏览器或申请桌面权限。

## 2. 模型可见接口

设备发现／状态是辅助接口；真正执行能力为三类。工具定义不按设备复制，每种工具只发布一份，通过设备参数选择目标。

| 能力 | v1 接口 | 适配边界 |
| --- | --- | --- |
| 发现与状态 | 保留 `list_execution_environments`、`get_execution_environment_status` | 扩展 Browser 能力和实际状态，保留现有字段语义 |
| Exec | 保留 `exec_command`、`write_stdin` | 保留命令、cwd、stdin、输出、PTY 和 owner 绑定；不为 git、curl、构建等分别造工具 |
| Browser | 复用锁定版本的 Playwright MCP 原生 `browser_*` 名称和 schema | 补必要的设备选择与调用归属，转发到 Host 上的 provider |
| Cua | 保留现有十个通用工具及名称 | 保留跨平台参数收敛、`environment_id`、隐藏原生 session 和引用归属校验 |

`environment_id` 沿用现有规则：存在明确默认设备时可省略；否则返回需要选择设备的错误，不猜测目标。Exec 的 `write_stdin` 继续从已拥有的句柄解析设备，不能被参数重定向。

Browser 初始范围：标签页管理、导航、网页快照、点击、输入／表单、按键、等待、截图、文件上传、网页对话框及下载结果。实现前核对上游实际工具清单，锁定 release、依赖与 schema 清单；不在运行时追随 `latest`。

不预先增加一整套 `browser_id/page_id/snapshot_id` 参数。先复用上游已验证的标签页及 `target` 引用机制；只有真实多设备／并发测试证明有必要时，才评审最小扩展。保留模型可见的结构化 schema，不把全部操作包进通用的 `call_tool(name, args)` 或自然语言 `execute_task`。

底层 Exec Server 不止两个 RPC。当前两个 MCP 工具足以运行绝大多数 CLI 工作，但取消、遗留工作查询与恢复需要单独完善。Core 的停止操作应使用底层已有进程控制并核对真实退出，不能把终止请求成功当成进程已退出。若后续需增加模型接口，优先核对已有成熟契约，不在本稿发明名称。

## 3. Agent 使用指引

- 命令、脚本、文件处理、构建、测试、交互式 PTY：通常直接使用 Exec。
- 网页内容与操作：通常使用 Browser；先利用网页定位、快照以及 Browser 自身的截图能力。
- 原生应用、浏览器外壳或需要真实桌面的部分：使用 Cua。Browser 不能完成时，由 Agent 根据观察决定是否使用它。
- Exec／Browser 失败时返回具体事实，不在本地偷偷改用 Cua。未知执行结果先观察、对账，不能自动重放。

这些是面向 Agent 的策略与评测要求。本地只检查设备与能力授权、身份和 owner、参数、原生权限及执行一致性，不判断用户任务应该走哪个工具。系统授权仍由用户本人完成。

共享策略放入插件 skill／简短服务器说明；每个工具只保留用途、关键约束和必要例子，删除重复的大段指导。

## 4. 单入口与按需发现

用户只创建／关联一个 Styx 插件；内部 provider 不要求用户再配置三份 MCP 或三套凭据。

**首版兼容路径：** 发布精简、稳定、确定排序的普通 MCP 目录。只声明实际支持、已授权且有可用 provider 的能力；已配置但暂时离线的能力保留可诊断状态，不让工具名随网络抖动反复消失。不能发布 Browser 空实现。工具集合真正改变时，使用标准变更通知，并验证客户端刷新行为。

**客户端支持时：** 使用其原生 Tool Search／按需加载。常用工具是否常驻由实际任务评测决定，不给所有客户端写死一套策略。

MCP 分页、工具名前缀和返回一段 schema 文本，本身不等于把新工具加载到模型上下文。OpenAI API、Codex、ChatGPT 插件的支持分别验证；不把某个 API 功能直接承诺给所有聊天端。

内部可以聚合 Exec、Playwright MCP、Cua 的协议连接，不增加本地模型。自建搜索代理、Code Mode、额外子 Agent 不作为 v1 前置条件；以后有性能证据再评审，保留同一套真实工具契约。

## 5. Browser 连接

Playwright 是操作接口；CDP 是连接已有 Chromium 浏览器的一种方式。两者不是两个相互竞争的模型工具组。

| 使用方式 | 接入方向 | 用户体验 |
| --- | --- | --- |
| 使用已有 Chrome／Edge 登录状态 | 优先验证官方 Playwright 扩展接入 | 用户在浏览器完成扩展安装、关联及必要确认；不能静默假定已接管日常浏览器 |
| 隔离自动化／headless | Styx 管理专用 Playwright 浏览器与 profile | 登录状态属于该 profile，不宣称自动继承日常浏览器登录 |
| 已有受控 CDP 浏览器 | 复用明确配置的本机连接 | 作为兼容接入方式；不默认开放调试端口或暴露给公网 |

日常默认浏览器关联与专用浏览器分别验收。浏览器连接地址、profile 路径和凭据来自 Core 私有配置，不作为每次工具调用的模型参数。

没有可见窗口的 headless 页面不能由 Cua 直接接管。Browser 的就绪不取决于 Cua 已就绪；Cua 的授权也不意味着浏览器已经关联。

## 6. 会话、结果与恢复

- 设备身份、MCP owner、Exec 句柄、浏览器进程／profile、网页上下文与 Cua 快照分别管理。
- MCP 新连接不必启动新浏览器，也不因此清空登录。复用同一登录 profile 不等于不同聊天拥有独立的登录状态；标签页、当前页和引用的归属必须单独保证。
- 不共享一个会被不同聊天互相切换的“全局当前标签页”。优先使用上游上下文隔离；对必须共享的已有页面核对并发与变更，不能靠连接数上限代替正确性。
- 重连重新发现实际资源与代次；旧引用失效要明确报错。不能自动复活旧进程句柄、复用旧网页元素或重放提交、点击。
- 沿用原生结果语义，保留结构化错误、截图和文件结果；连接、发送成功、实际完成、页面读回和聊天账号验收分开记录。
- 运行负载、未取结果和历史记录分别对账与回收。保留已移除的 Exec 数量拒绝修复，不新增累计命令数或会话数门槛，不静默驱逐活跃任务。

App／CLI／onboarding 使用相同 Core 配置和生命周期；Browser 能力进入现有受控配置与服务事务，不增加独立且冲突的角色配置文件。后台、注销、重启与 App 退出的行为按实际浏览器运行方式观察，不能从 enabled 推断运行正常。

已有 CAS Run/Wake 续接继续作为独立任务生命周期能力保留。工具目录分层不替代长期任务集成，也不把 CAS-only 实验自动接入普通执行连接。

## 7. 普通用户 onboarding

1. 安装 Styx，选择本机使用或加入已有主台，按需启用 Exec／Browser／Cua。
2. 完成本机准备、Browser 关联和所需系统授权；后台运行独立选择。
3. 主台准备聊天入口，明确目标账号／工作区。
4. **首次创建插件**：确认名称、描述、可选图标，进入受支持的官方创建流程；支持 Plugin Creator 时可交接生成包。官方直接创建不应强制先导出 ZIP。
5. **关联已有插件**：定位并核对原插件，在目标账号安装／启用并完成连接；重装与 Host 加入不重复创建插件、Gateway 或隧道。
6. 回到真实聊天，分别验证所选 Exec、Browser、Cua 能力，再确认结果来自目标聊天。

App 必须有可操作的“创建新插件／关联已有插件”入口。保存资料、生成 ZIP 或用户勾选确认不能显示成平台创建、安装或连接成功。平台返回的标识原样保留；插件 URL 只是定位入口，不证明账号身份。

官方登录、账号选择、MFA、授权及浏览器扩展确认由用户完成；能自动处理的本机步骤由 Core 执行。需要 Codex 协助上传时，提供具体、无密钥的交接材料；不虚构 App 可直接调用的账号上传 API。

Bearer 要求以真实隧道／插件认证验收为准。当前上游声明与隧道本机注入同时存在，先核对再简化；不承诺未经验证的免认证路径。

## 8. 分阶段交付与验收

| 阶段 | 可交付结果 | 必须验证 |
| --- | --- | --- |
| A：目录精简与插件接入 | 稳定短描述；App 的创建／关联与继续引导入口 | 普通用户从本机设置走到真实插件调用；重装复用，加入主台不重复创建；既有身份、授权及进度保留 |
| B：Browser provider | 复用成熟契约，接入同一 Core、Host 与 Gateway | 真实浏览器发现／标签页／表单／下载、登录状态、两个聊天并发、过期引用、断连恢复及 headless 状态 |
| C：选择效率评测 | 对支持的客户端选择兼容目录或按需加载 | 同一任务集比较完成率、错误工具选择、首个正确调用耗时、输入量及调用次数；覆盖 CLI、网页、桌面和混合任务 |
| D：安装包与原生验收 | 可重复构建、迁移与回滚收据、新安装包 | Pilot Mac 真实首装／续装、文件面板、目标账号调用；Windows 与跨设备按独立证据报告 |

每阶段区分已实现、已测试、已打包、已部署和未验收。Browser 完成前的包只能说明已经交付的能力，不称“三类能力完整正式版”。piermini／NAB 线上变更仍需协调。

## 9. 当前基线与下一步

当前已有 Exec、Cua、多设备基础及部分插件引导源码；Browser provider 与客户端按需加载尚未接入。已交付 Pilot Mac 的 dev.2 基于 `d8555ea`，不含后续插件引导补充。

下一步先完成 A，并核对 B 的既有浏览器方案和锁定上游接口；A 可先提供明确标注范围的候选包，B 单独达到真实验收后再纳入。原生界面视觉重写后置。

本文不新增配置格式、工具名或运行逻辑。后续实现先提交具体 schema 差异和兼容性测试；账号上传方式、默认浏览器关联及按需加载的实际可用性以目标客户端验收为准。
