# Thin Browser native worker

This is the external Node Browser executor, not a second Styx Host. Rust alone owns authorization, owner/principal/profile/resource binding, URL and file policy, serialization, snapshots, cancellation certainty, Unknown history, persistence decisions and cleanup admission. This process has one task-private persistent headless context. It does not restore canonical login state, select another profile, reconnect or replay actions.

Start with the pinned Node22 executable:

`node worker.mjs --config /absolute/private/startup.json`

The Rust-created0600 configuration has exactly `schema:1`, `profile_dir`, `output_dir`, `workspace_dir`, `browser_executable`. The three directories are canonical absolute paths and already exist. Config and browser executable also accept only the strict Linux kernel `/proc/<positive-pid>/fd/<decimal-fd>` form for Rust-held File pins; other symlink/path forms remain rejected. The worker does not treat PPID as source authority because an owned systemd scope can reparent it; the Rust fixed launch factory owns the pinned PID/FD source. These FD paths are read/opened and validated through fstat, while Rust retains the source files until child reaping. Profile must not overlap workspace/output. Unix ownership/private modes are defensively checked here; Windows ACL authority belongs to the Rust native adapter and is not attested by Unix mode bits. Configuration contains no Gateway/admin/enrollment credentials.

The stdio protocol is the official MCP SDK StdioServerTransport, not a custom framing or RPC implementation. The SDK incoming read buffer is256KiB. Responses and SDK/Playwright transient allocations are not claimed to have that hard memory bound; Rust must bound admission/output and supervise worker/process limits. The Node server delegates list/call via the official SDK in-memory client to `@playwright/mcp.createConnection`. Rust admits only its explicitly implemented typed tool subset under fresh Core policy, independently of the full upstream listing; listing a backend tool does not authorize it.

Launch is exclusively `chromium.launchPersistentContext` with `headless:true`, `chromiumSandbox:true`, the explicit executable, a1280x800 viewport and the scoped download/output directory. There are no arbitrary Chromium arguments, no `--no-sandbox`, browser download or headed/attach mode. A single cached launch promise is retained after failure/closure; no subsequent call relaunches. PWDEBUG is removed to prevent debug headed takeover. Rust should start Node with a controlled environment and task-private HOME/TMP.

Upstream `browser_close` disposes its supplied-context tabs without closing the owned persistent context. This wrapper awaits the original call, then closes that exact context and adds `structuredContent.styx_context_closed:true` only after actual `context.close()` resolves. It keeps stdio open long enough to deliver the reply. Rust then closes its SDK client/stdin and waits for Node/pipe termination. Node also awaits context closure on stdin EOF, SIGTERM or transport failure; a process exit or this marker alone is not an independent kernel proof that all Chromium descendants exited. Native stderr events are lossy hints (64KiB lifetime budget, coalesced under backpressure), not an audit log. They report page/navigation/context lifecycle facts only; they contain no URL, owner, capability grant or trusted snapshot reference.

Dependencies are pinned in this directory's package/lock: official SDK1.32.1, Playwright MCP0.0.83 and Playwright1.64.0-alpha-1790635538000. They must be installed/shipped as the adjacent `node_modules` closure. Runtime code never imports another worktree, the legacy host supervisor or a global package. The development closure can be copied/COW from the byte-locked legacy provider, without modifying that provider. Shipped manifest/bootstrap integration remains a separate release task; this source directory and a successful development scenario are not a signed package.

## Native factual epoch (worker protocol0.2.0)

The internal `styx_browser_state` MCP tool reads `{schema:1,epoch,ready,closed}` in structuredContent without starting a context or calling the native backend. Before first native launch epoch is1, ready is false and closed is false. Ready means the owned context has been obtained and is currently dispatchable; closed means an observed context-close event or exhausted safe epoch counter. A worker closing/failing can reject dispatch before its context-close event is observed, so ready=false/closed=false is not permission to run. Neither value is process-exit/cleanup proof. The state tool accepts no arguments; it remains readable after context closure. Its metadata has before=after=current epoch and dispatched=false. State reads ignore a well-shaped expected_epoch condition, allowing explicit observation of current facts; malformed conditions are rejected.

Page discovery, frame navigation, page close and context close advance the monotonic safe integer. Each forwarded browser_tabs action new/close/select also advances, even if the backend later fails; list does not advance. Browser event delivery can advance it again. At MAX_SAFE_INTEGER the next advance marks exhaustion and closes dispatch, schedules existing owned cleanup, and never wraps or reuses the epoch. It is a backend lifetime/freshness fact, not a Styx owner, grant, observation reference, session selection or policy authority.

Optional request params._meta['app.styx/browser-native'] must be exactly `{schema:1,expected_epoch:N}` with a positive safe integer. Invalid shape returns isError=true and wrapper metadata `{schema:1,before:E,after:E,dispatched:false,reason:'invalid'}`. A mismatching epoch or closed/closing backend returns the same shape with reason='stale' before forwarding any backend call. The guard and invocation have no intervening await. Absence preserves the unconditioned internal executor interface; Rust decides which tools/actions require a factual epoch under current Core policy.

All truly forwarded calls, including error/unconfirmed results, have wrapper-overwritten result _meta['app.styx/browser-native'] equal to `{schema:1,before:E,after:F,dispatched:true}`. Other upstream result metadata is retained, but the reserved key is always replaced; backend content cannot fake NotSent or freshness. Dispatched means the wrapper invoked its backend call, not that an action succeeded. A backend/transport exception is a generic error with dispatched=true and must stay Unknown at the Rust boundary; it is never automatically retried. before/after changes invalidate any older native observation; they do not by themselves create a new trusted Styx reference.

listTools appends the internal state schema while preserving upstream schemas. Runtime must remove this one internal schema before validating the exact frozen upstream tool contract. SDK input buffering still does not bound native V8/Chromium heap or output serialization; native cgroup supervision and Rust queued-I/O accounting remain separate responsibilities.

For a real browser tool only, the wrapper first rejects malformed/already-stale conditions, then awaits the same cached owned-context getter used by the upstream backend. Initialization/list/state remain lazy and never call that getter. Once initial owned context/page lifecycle observations are installed, the wrapper synchronously rechecks closing/closed/expected_epoch, captures before, and invokes the original MCP tool without an intervening await. This permits an unconditioned first Snapshot to observe an already initialized context without counting that bootstrap as a mid-snapshot page change. An expected_epoch from before initialization can become stale and is still rejected; the caller must not treat ready=false as a stable page observation. Context initialization failure is a generic RPC error/Unknown, not a fabricated NotSent tool result. The cached failed promise is retained. Later events still change after and invalidate a snapshot; no snapshot/action retry, epoch relaxation or replacement context occurs.
